# project-setup Specification

## Purpose
How one command brings a project — empty or already working — to a harnessed state: what
it asks, what it surveys before it decides, the plan it shows, what stops it, what it
creates, what it only proposes, and why running it a second time changes nothing.

## Requirements

### Requirement: One command sets a project up, and asks before it acts

The harness SHALL provide a single command that brings a project to a harnessed state.
That command SHALL gather the project's choices, SHALL show what it intends to do, and
SHALL make no change to the project until the person has approved that intention.

#### Scenario: An empty project

- **WHEN** the command is run in a project that has never been harnessed and the person
  approves the plan
- **THEN** the project ends with the files the harness needs, the rules of the sets chosen,
  the project's recorded answers, the permission entries of the floor and the record of what
  was generated, and the command reports each path it wrote

#### Scenario: Approval withheld

- **WHEN** the plan is shown and the person does not approve it
- **THEN** no path is created, modified or removed, and the command says that nothing was
  written

### Requirement: Setup offers only what the harness holds

The command SHALL ask only for choices it cannot derive, and every choice it offers SHALL
be derived from what the harness itself holds rather than from a list kept beside it. A
kind of choice for which the harness holds nothing SHALL NOT be asked about, and SHALL be
recorded as an empty choice. An answer naming something the harness does not hold SHALL
stop the run before anything is written.

#### Scenario: Choosing among what exists

- **WHEN** the command asks which rule sets the project wants
- **THEN** the sets offered are those the harness holds, so a set added to the harness is
  offered and a set removed from it is not

#### Scenario: A kind of choice with nothing to choose from

- **WHEN** the harness holds no member of a kind of choice the project's answers record
- **THEN** the command does not ask that question, records the choice as empty, and needs no
  change to offer it once the harness holds one

#### Scenario: An answer the harness cannot honour

- **WHEN** an answer names something the harness does not hold
- **THEN** the command stops, names what was asked for, lists what it holds, and writes
  nothing

### Requirement: Setup surveys every path before it plans

Before planning, the command SHALL inspect every path it could touch and classify it as
absent, generated by the harness, owned by the project and present, or present but
unaccounted for. The classification SHALL come from the recorded generation metadata and
the content of the path, never from its mere presence.

#### Scenario: Classifying what is there

- **WHEN** the survey runs in a project holding some of the harness's paths and some of its
  own
- **THEN** each path is reported with its classification, and a harness-owned path whose
  content matches the record is distinguished from one whose content does not

#### Scenario: A harness-owned path the harness did not write

- **WHEN** a path the harness owns is present and no record accounts for its content
- **THEN** it is classified as unaccounted for and the run treats it as a conflict

### Requirement: Setup prints a plan, one line per path

The command SHALL print, for every path in the survey, what it would do to it — create,
leave alone, propose an insertion, merge entries, or report a conflict — before it writes
anything. The plan SHALL be readable without reading any other document.

#### Scenario: Reading the plan

- **WHEN** the plan is printed for a project with paths in several classifications
- **THEN** every path appears exactly once with the action intended for it, and a path the
  command will not touch says so rather than being omitted

### Requirement: A conflict stops the run before any write

The command SHALL stop, without writing anything, when the plan contains any conflict. It
SHALL name every conflict, say how each can be resolved, and SHALL NOT resolve one on its
own.

#### Scenario: An unaccounted-for harness file

- **WHEN** the plan reports a harness-owned file present but unaccounted for
- **THEN** the command stops before any write, names the file, and offers the choice of
  moving it aside or letting the harness adopt it after showing the difference

#### Scenario: More than one conflict

- **WHEN** the plan contains several conflicts
- **THEN** all of them are reported in one run, so resolving them does not require running
  the command once per conflict

### Requirement: The project's own files are never rewritten

A file the project owns SHALL NOT be modified by the harness except by inserting a line the
person explicitly approved, and SHALL NOT be created when it already exists. When the
harness creates such a file, it SHALL be created from a template that names no particular
project.

#### Scenario: An entry file without the harness's pointer line

- **WHEN** a file the project's tools read first exists but does not tell them where the
  rules are
- **THEN** the command shows the exact line it would insert and where it would go, and
  inserts it only after an explicit yes

#### Scenario: The insertion is declined

- **WHEN** the person declines the insertion
- **THEN** the command finishes the rest of its work, states which tool will not read the
  rules as a result, and repeats that notice on every later run

#### Scenario: A project file that already says what is needed

- **WHEN** an entry file already carries the pointer line
- **THEN** the file is left byte-identical and the plan says so

### Requirement: The project's choices are recorded where both sides read them

The command SHALL record the project's answers — its name, the profiles and rule sets and
features chosen, the canary word, the decision backend and the command that checks the
project — in one file that belongs to the project. That file SHALL be created only when
absent, and SHALL be read as the input of every later harness operation rather than being
rewritten by one.

#### Scenario: Reading the choices back

- **WHEN** any harness component needs to know what the project chose
- **THEN** it reads that one file, and every choice the command asked for is present in it

#### Scenario: The choices already recorded

- **WHEN** the command runs in a project whose answers are already recorded
- **THEN** it takes them as its input, does not ask again, and leaves the file unchanged

### Requirement: The rules the project reads come from the sets it chose

The command SHALL produce the project's rules file from the sets recorded in the project's
choices, and SHALL produce it through the harness's rendering rather than by copying rule
files. Changing the recorded sets and running the command again SHALL produce the rules
file for the new choice.

#### Scenario: Rendering for the project

- **WHEN** setup completes in a project that chose a list of sets
- **THEN** the project's rules file holds every rule of those sets and no rule of any set
  not chosen

#### Scenario: The choice changes

- **WHEN** the recorded sets are changed and the command is run again on a rules file that
  the harness wrote and nobody edited
- **THEN** the rules file is re-rendered for the new choice and the record updated

### Requirement: Running setup again changes nothing

Run a second time on a project whose choices and harness content have not changed, the
command SHALL report that there is nothing to do and SHALL leave every path byte-identical,
including the record of what was generated.

#### Scenario: A second run

- **WHEN** the command is run twice in succession with no change in between
- **THEN** the second run plans nothing to do and no byte of the project changes

#### Scenario: A fresh clone of a harnessed project

- **WHEN** a project that was set up is cloned fresh and the command is run in the clone
- **THEN** it recognises the project as already harnessed from the committed record, asks
  nothing, and plans to restore only the runtime state location, which is deliberately not
  committed; every committed path is reported unchanged

### Requirement: Runtime state stays out of the project's history without touching the project's rules

The command SHALL place the runtime state the harness writes at task time in one location
that excludes itself from version control, and SHALL NOT modify the project's own
version-control exclusions to achieve it.

#### Scenario: After setup

- **WHEN** setup has completed
- **THEN** the runtime state location excludes itself, and the project's own exclusion file
  is byte-identical or still absent

### Requirement: An interrupted setup completes on the next run

The command SHALL be safe to interrupt at any point. Run again after an interruption, it
SHALL complete the remaining work without redoing what is already correct and without
asking the person to repair anything by hand.

#### Scenario: Interrupted after a write

- **WHEN** the command is interrupted after any one of its writes and then run again
- **THEN** it completes, the project ends in the same state as an uninterrupted run, and no
  path is left partially written
