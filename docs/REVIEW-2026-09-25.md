# Plan review — 2026-09-25

An external review of `docs/PLAN.md` (v2), taken after `C1b` landed and before `C1c`
opened. The reviewer kept the five pillars, the three roles and the incremental delivery,
and found the weaknesses in two places: adopting an existing project, and guarantees the
design stated but could not deliver. Every finding was checked against the plan, the
code, the diagrams and the Claude Code documentation for 2.1.267 before being applied.
Plan v2.1 applies all of them; this file keeps the findings, the verdict and where each
one landed, so the plan has one source.

Facts marked **verified** were checked against the Claude Code docs (hooks, permissions,
sub-agents, plugin components).

## Findings

### 1 · High — setup did not say how to adopt an existing project

The plan promised both that an existing `AGENTS.md` is never touched and that its first
line tells Codex to read the rules file: with an `AGENTS.md` that lacks the line, both
cannot hold. What happens to an existing `CLAUDE.md` or `.claude/settings.json` was not
defined.

**Verdict: accepted.** Landed in §6: entry files (`AGENTS.md`, `CLAUDE.md`) and the
OpenSpec config belong to the project; the harness asks for its pointer lines and inserts
them only on an explicit yes; setup surveys, prints a plan, stops on any conflict before
writing, and only then writes. `.claude/settings.json` becomes the one file owned by entry
(below). C1c now proves adoption on an existing project as well as an empty one.

### 2 · High — "the guard never fails open" exceeded what a hook can offer

The script can answer *ask* when it catches an error, but a hook that does not start,
hangs, or is killed at its timeout cannot answer at all. **Verified:** a timed-out
command hook, a missing executable and malformed output are non-blocking errors, and the
tool call continues through the normal permission flow; there is no fail-closed setting.
**Verified:** a plugin cannot ship permission rules — of a plugin's settings only `agent`
and `subagentStatusLine` take effect.

**Verdict: accepted.** Landed in §9: two failure classes, only one in the script's hands;
a permission floor in the project's `.claude/settings.json` carrying the guard's deny and
ask patterns, written by setup because the plugin cannot; the hook's timeout set above the
script's budget. C4 tests the hook as a real process — hanging backend, crash, missing
interpreter, external timeout — and checks the floor covers every pattern.

### 3 · High — role boundaries had no defined enforcement coverage

The builder is Codex, whose guard is a later feature, yet diagram 04 said the guard keeps
the builder from ticking tasks, committing and widening scope. A Bash hook does not see
`Edit` or `Write`. **Verified:** permission rules in `settings.json` apply to the whole
session, subagents included; per-subagent limits come from the `tools` list, and a hook
can tell a subagent's call by the `agent_type` field in its input.

**Verdict: accepted.** Landed in §4: a rule × actor × mechanism matrix distinguishing
instruction, prevention and detection, and a plain statement that v0.1 holds the builder
by instruction plus deterministic detection before acceptance. Diagram 04 corrected.

### 4 · Medium — the update contract lost its reference in a fresh clone

The hash manifest lived in `.harnex/state/`, which is not committed, so a collaborator's
clone had the generated files but nothing to tell them from edited ones. The plan also
said `update` reads `.harnex.yml` and that it never reads project-owned files.

**Verdict: accepted.** Landed in §6: generation metadata moves to `.harnex/manifest.json`,
committed; `.harnex/state/` keeps only the journal and run state and ignores itself;
update's reads and writes are stated separately; an interrupted update recovers by
content (a file matching either the old or the new hash is safe); a missing manifest
sends you to adoption rather than guessing. The contract is fixed in C1c, though the
command lands in C6.

### 5 · Medium — the canary claimed a diagnosis it cannot make

A missing word proves that one instruction was not followed, not that the context was
lost, and a present word proves nothing about the other rules. The `canary` set was
selectable, yet C1d applied a default word even without `.harnex.yml`.

**Verdict: accepted.** Landed in §3 and C1d: the warning is a signal of possible
non-compliance; the check is active only when `.harnex.yml` exists and chooses the set;
the hook has no fallback word. Tests cover an unconfigured project and one without the
set. The `canary` rule's wording is revised inside C1d, since it lives under `plugin/`.

### 6 · Medium — the apply loop had no recovery contract

Nobody was named to tick `tasks.md` or with what evidence; an interrupted delegation had
no defined outcome; diagram 04's retry went straight back to the check with no fix.

**Verdict: accepted.** Landed in a new §10: only `apply` ticks, on facts (exit code, path
containment, protected paths, refs unmoved); evidence is bound to a working-tree
fingerprint; a retry is one builder fix; every transition is recorded and an interrupted
run resumes from that record or asks. Diagram 04 corrected.

### 7 · Medium — some dependencies between phases arrived late

C2 used the verifier that C5 delivered; the viability of delegating to Codex was tested
in C3; the first adoption of an existing project waited for C6.

**Verdict: accepted.** A minimal read-only verifier ships with C2 and C5 extends it; the
Codex spike becomes S1 and runs before C2; adoption is proven in C1c. The phases keep
their order; the checks that could invalidate later decisions move forward.

### Minor

- **An `httpx` client against decision 15 (standard library only).** Accepted: the Jev
  client uses `urllib`.
- **Routing claimed to pick a model where it can only advise.** Accepted: the decision
  line is binding where harnex delegates and marked as advice for main-session phases.

## Found while applying the review

- **The plugin's hooks run in every project on the machine**, because the plugin is
  installed per machine. Every harnex hook is now inert without `.harnex.yml` (decision
  19).
- **Scope has a factual half.** Whether changed paths sit inside a task's declared paths
  is a set comparison, so it is checked, not asked; `task.scope` remains for tasks that
  declare no paths.
- **The rule sets were not a `.harnex.yml` key**, although §7 said they are recorded
  there. `sets` joins the fixed names; the canary's activation depends on it.
- **The Stop hook question is answered by the docs**: the input carries
  `last_assistant_message`. C1d records a real payload instead of running a spike.
