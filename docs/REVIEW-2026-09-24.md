## B. Scope for v0.1 (devil's advocate)

- The first objective is a **move, not a build**: the generic material already exists and
  is under 700 lines (four stack agents, one hook, one permissions allowlist, two MCP
  wrappers, ~20 lines of generic rules). Phases 2–6 propose ~50 new artifacts before any of
  it is importable.
- Proposed walking skeleton: `copier.yml` with `project_name` + `profiles` (multiselect);
  renders `AGENTS.md` (generic rules), `CLAUDE.md` (`@AGENTS.md`), profile agents,
  `.claude/settings.json` (permissions + hook), the hook script, `.mcp.json`. Import into
  one existing project, deprecate the old marketplace. CI: render with `--defaults`,
  snapshot the tree, validate frontmatter, grep a denylist of private names.
- Cuts proposed: the six `sdd-*` skills (OpenSpec 1.11 already installs twelve equivalents
  into both tools; the template must never write `openspec-*` or `.claude/commands/opsx/`);
  keep one new skill, `delegate-task`. Roles: `architect` = Claude running OpenSpec
  propose, `orchestrator` = human; merge `verifier`+`reviewer`; `designer` = react flavour
  of `builder`. Rules: one file with sections, no frontmatter engine until a second
  project needs a different selection. Jev: none in v0.1. Runtime CLI: none until needed.
  Docs: README + `DECISIONS.md`.
- Slice by **capability**, not by pillar (pillars stay as layout and vocabulary):
  S1 import · S2 update · S3 guard (first stated+enforced rule) · S4 delegate to Codex
  (timeboxed spike first) · S5 release.
- Decide now (expensive to change later): Copier question names and answers-file keys,
  template root (`_subdirectory`), how dual placement `.claude/` + `.agents/` is rendered,
  the path of the harness-owned rules file that `AGENTS.md` points to, tag scheme and
  "verified against" versions, agent/skill frontmatter minimum (`name`, `description`,
  `tools`). Leave open: rule frontmatter, Jev YAML, journal schema, run state machine.
- Testability: Claude/Codex/Jev need credentials; CI uses a lighter checker. Per slice:
  snapshot render (S1), tag-to-tag update (S2), pytest over hook stdin fixtures (S3), fake
  `codex` on PATH recording argv (S4), manual `docs/smoke.md` with versions (S5).

## C. Import mechanism (Copier 9.18.2, verified by experiment)

- `copier update` = render old, render new, `git diff` old→project, overwrite with new,
  `git apply --reject`, `git merge-file`. **No ownership concept**: every file is 3-way
  merged. Markers in `AGENTS.md` are ignored by Copier; empirically they work when the
  project edits outside the section, conflict (`<<<<<<<`, `UU` index) when inside.
- Idiomatic ownership = one file per owner: project-owned files in `_skip_if_exists`.
- `.claude/settings.json` merge with project content **cannot** be done in the template:
  `_external_data` resolves against the temp render dir during `update` and silently
  returns `{}`. Options: harness-owned `settings.json` rendered from answers; or a CLI
  step deep-merging `settings.harnex.json` + `settings.project.json`; or deliver
  hooks/permissions as a plugin (Claude merges lists across scopes).
- Existing project: `copier copy` aborts on conflict non-interactively; `--overwrite`
  destroys the existing `AGENTS.md`; `--skip` keeps it but breaks the update baseline
  (open issue copier#2486 "adopt"). `update` needs a git repo, a clean tree, and tags
  (default ref = latest PEP 440 tag; untagged → `_commit` hash, migrations never fire).
- `gh:ppalomo/harnex` works; `copier.yml` at root with `_subdirectory: template` works;
  set `_answers_file: .copier-answers.harnex.yml` to coexist with other templates.
- "Second update is a no-op" holds with clean tree + `--skip-answered` + no external data.
- Sharp edges: renaming a harness-owned file silently drops project edits (needs
  `_migrations`); deletions propagate; `_tasks`/`_migrations` require `--trust`; new
  questions need defaults.
- Alternatives: git subtree (no rendering, no fit); `harnex sync` with manifest + hashes
  (exactly the stated ownership contract, native adoption and JSON merge, no `--trust`, no
  clean-tree rule; loses in-file merge, which only matters if `AGENTS.md` stays shared);
  plugins — **Codex now has plugins too** (`.agents/plugins/marketplace.json`, skills,
  hooks, mcp), so a hybrid (plugins for skills/hooks/agents/MCP in both tools, template or
  sync for `AGENTS.md`/permissions/openspec) is possible at the price of two mechanisms.

## D. Claude Code 2.1.267 and Codex 0.155.1 (verified)

- `CLAUDE.md` = `@AGENTS.md` works (imports up to 4 hops). Codex reads the root
  `AGENTS.md` directly, concatenated root-down; it has no import syntax, but none is
  needed for a shared root file. It IS needed if harness rules live in a separate file:
  then `AGENTS.md` must tell Codex to read it in prose.
- SKILL.md portable core is `name` + `description` + body. Claude-only keys
  (`allowed-tools`, `disable-model-invocation`, `context: fork`, `agent:`) break the
  one-copy idea; keep skills to the core.
- Codex custom agents are TOML at `.codex/agents/*.toml` (`model`, `sandbox_mode`,
  `mcp_servers`, `developer_instructions`); Claude agents are Markdown+YAML. No shared
  format. Roles reach Codex as prose/skills unless TOML is also maintained.
- Claude `PreToolUse` on `Bash`: exit 2 or JSON `permissionDecision: deny|ask|allow`;
  `if: "Bash(...)"` narrows the trigger; default timeout 600 s; a crashed or timed-out
  hook **does not block** (fail-open to the permission mode).
- **Codex has hooks** (`PreToolUse`/`PostToolUse`/`PermissionRequest` in `hooks.json`,
  `--dangerously-bypass-hook-trust` flag exists) plus execution-policy rules and
  `codex exec --sandbox … --worktree --json`. The plan's "Codex has no per-command hook"
  is out of date: one guard script can serve both actors.
- `claude -p`: `--output-format json`, `--allowedTools`, `--permission-mode`, `--agents`,
  `--append-system-prompt` exist; `--max-turns` is **not** in `--help`. For a Python
  runtime the Agent SDK (turn control, session, cost) fits better than a subprocess.
- `settings.json` precedence: managed → CLI → project local → shared project → user;
  list keys (`permissions.allow`, `hooks`) merge across scopes.
- Official `codex@openai-codex` plugin for Claude Code: `/codex:review`,
  `/codex:adversarial-review`, `/codex:rescue` (background delegation), `/codex:transfer`,
  status/result/cancel. Direct `codex exec --worktree` is simpler for an orchestrator;
  the plugin is better for interactive delegation. Spike before choosing.

## E. Jev and the automatic loop (verified against OpenRouter, TypeSafe docs, BenchLM)

- Facts: OpenRouter endpoint is **alpha** (`typesafe/jev-1.13`); TypeSafe direct signup
  paused 2026-09-22; 32k real bound; Noul returns a probability and **no confidence**;
  Choice/Score return `probabilities` + `confidence`, and confidence is a distribution
  statistic (≈ `(n·p_max − 1)/(n − 1)`), so one threshold means different things per option
  count; Score returns a fractional position; one integrator saw ~15% read-timeout hangs;
  documented failure modes: literal reading, counting, multi-hop, large state,
  **adversarial text in state moves the answer**, no invariants across answers.
  `typesafe-sdk` cannot be pointed at OpenRouter (different path); use OpenRouter's SDK
  or a small httpx client with retries.
- `guard.risk`: sound, but decide on `P(destructive)` from `probabilities`, and never send
  the model's own `description` of its command (self-arguing text). `plan.complete` as one
  Noul over four artifacts is **wishful** (multi-hop, large state, ~2/3 agreement on
  workflow judgments): decompose into narrow questions or use `openspec validate` +
  linter + the reviewer. `task.route`: fine, but criteria must be literal. `task.done`:
  check exit code is the fact; Jev can answer "changed paths within declared scope"; diff
  semantics is System 2 work. `change.ready`: redundant if findings carry severity.
- Thresholds "accept >0.85 / escalate <0.50" are incoherent across types (a Noul at 0.05
  is a confident no, not an escalation). Each question declares its own rule on
  `probabilities`. "Retries once" is undefined (re-ask vs rebuild).
- Guard decision table: (0) parse with shlex, split on `; && || | $( )`, unparseable →
  ambiguous; (1) all segments in read-only allowlist → allow, no Jev, no journal;
  (2) deny patterns (`rm -rf` outside cwd, force push, `reset --hard`, `clean -f`, `sudo`,
  `dd`, `mkfs`, `curl | sh`) → deny, journal; (3) ask patterns (`rm` in cwd, `git push`,
  `rebase`, `docker`, `kubectl`) → ask, no Jev; (4) residue → Jev with
  `{command, cwd, branch, is_worktree}`, hook timeout 3 s, one retry; (5) Jev unreachable
  or off → **ask** with reason. Deny never comes from Jev alone.
- Jev off must be first-class: every question has a documented no-Jev behaviour
  (`NullOracle` → ask the human / exit code / severity filter); phase exit criteria are met
  with Jev disabled first.
- Journal needs `resolution` (human override or downstream outcome) or thresholds cannot
  be tuned. Proposed fields: `run_id, change, task, attempt, question, state_sha256,
  probabilities, confidence, decision, rule_applied, actor, cost, resolution`.
- Runtime prerequisites that manual mode already touches: check-command declared in one
  place (answers file / `AGENTS.md` harness section) and read by agents, hooks and
  runtime alike; one worktree per change with sequential tasks; `tasks.md` linear in file
  order (no DAG in 0.1); disagreement rule (any blocking finding blocks; conflicting
  non-blocking → human). Phase 8 proper: state machine persisted at
  `.harnex/runs/<change>/state.json`, resume by state not replay, idempotent side effects
  keyed `(change, task, attempt)`, retry budget (2 per task, 1 escalation per change),
  wall-clock budget, SIGINT → cancelled, escalation may rewrite `tasks.md` mid-run,
  builder prompt assembly. Split phase 8 into 8a (orchestrator, `codex` hard-coded, no Jev)
  and 8b (Jev routing and gates).
- Cost claim: Jev for one change ≈ $0.002 (rounding error). The real saving is the
  runtime giving each role a **fresh bounded context** so ~50–100k tokens of logistics
  never reach Claude; Codex does the bulk in both modes. Any structured-output small
  model captures the same saving; Jev's real advantages are latency and schema guarantee.
- Keep `run` behind a package boundary (`harnex[run]` extra or workspace package) so it
  can move out; a separate repo is premature.

## F. Pillar coherence (editorial fixes unless marked as owner decision)

- Check-command contract appears in `tools/sandbox/` and `feedback/checks/` → feedback
  only. `tools/sandbox/` holds no sandbox: worktrees are orchestration (checkpoints), the
  only real sandbox is Codex's (control). Dissolve it; pillar 2 keeps `skills/` and `mcp/`.
- Pillar table double-assigns "sandbox" (2 and 4): isolation environment vs restriction.
- Placement criterion is undefined; de facto it is by topic. State it: `harness/` is
  declarative (prompts, YAML, rules), `runtime/` executes; placement by topic. Otherwise

- `runtime/` outside the pillars is a leak unless the declarative/executable rule is stated;
  `harnex run` is pillar 3's core loop and `harnex guard` is pillar 4's enforcement.

  only in `profiles/`) → `profiles/<name>/rules/`.
- `task.route → claude` has no role Claude may play (`builder` is Codex-only) → owner
  decision: `builder` playable by Claude, or route only `codex`/`human`.
- Three incompatible statements of Jev in manual mode (guard only / gates ask human /
  guard and gates); `build` exit criterion unmeetable in manual mode without "or human
  accepts".
- Phase 3 delivers workflow skills before the workflow (phase 4); phase 4's exit needs
  phase 6's verify. Re-slice (see B).
- Pillar-5 hooks and pillar-4 restrictions reach only Claude while Codex builds → now
  fixable, Codex has hooks.
- Named but never delivered: compaction rules, external memory/RAG, sandboxes as

- Reviewer independence: Claude reviewing Claude's design needs a fresh session with only

- Minor: journal classified as both state (1) and observability (5); orchestrator cannot
