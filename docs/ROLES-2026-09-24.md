# Role study — 2026-09-24

What the field converges on, what each tool supports, and the role set harnex v0.1 adopts.
Decisions at the end are taken; the plan rewrite builds on them.

## What the field does

- Anthropic's harness for long-running app builds uses three roles: planner, generator,
  evaluator. The lever is separating the agent doing the work from the agent judging it,
  because models praise their own output. Every harness component "encodes an assumption
  about what the model can't do on its own", so roles should be removable.
  https://www.anthropic.com/engineering/harness-design-long-running-apps
- Orchestrator-workers and evaluator-optimizer are the two shapes harnex combines.
  https://www.anthropic.com/engineering/building-effective-agents
- Long-running agents: fresh context per session, a progress file plus git history as the
  handoff. https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- Claude Code recommends a writer/reviewer split across sessions ("a fresh context improves
  code review since Claude won't be biased toward code it just wrote"); built-in subagents
  are only Explore, Plan and general-purpose.
  https://code.claude.com/docs/en/best-practices · https://code.claude.com/docs/en/sub-agents
- Codex ships `default`, `worker`, `explorer` agents and a dedicated `codex review` that
  reports findings without touching the tree.
  https://learn.chatgpt.com/docs/agent-configuration/subagents · https://learn.chatgpt.com/docs/code-review
- Community: superpowers has no role files, only workflow skills (brainstorm, plan,
  execute per fresh subagent, review, finish). GSD Core: discuss/plan/execute/verify/ship
  with a clean context per executor. BMAD keeps five personas. Agent OS retired its roles
  system as "too complex". https://github.com/obra/superpowers ·
  https://github.com/open-gsd/gsd-core · https://docs.bmad-method.org/reference/skills-and-agents/ ·
  https://github.com/buildermethods/agent-os/discussions/310
- Evidence: cross-context review beats same-session self-review (F1 28.6 vs 24.6,
  p=0.008); repeating the review in the same session gives no gain. The difference is
  context, not repetition. https://arxiv.org/html/2603.12123

Net: the convergent taxonomy is **plan / build / judge**, with the judge in a fresh context.
Nobody successful keeps six roles.

## Role set for v0.1

| Role | Purpose | Default player | May write | Must refuse | Commands |
|---|---|---|---|---|---|
| `architect` | explore, decide, write the change artifacts, hand tasks out | Claude, main session (`opus`; `fable` for hard designs) | `openspec/changes/<x>/*` | source, tests, commits | explore, propose |
| `builder` | implement one task in a worktree, run the check command, report evidence | Codex via `codex exec`; Claude subagent as fallback so routing to Claude has a player | source and tests within the task's declared paths | ticking `tasks.md`, committing, editing specs, scope creep | apply |
| `verifier` | judge a design or a diff against specs and the running app; report only | Claude subagent, fresh context (`opus`, `effort: high`); `codex review` as optional cross-vendor second opinion | nothing | fixing, editing, committing, reopening settled decisions | propose (design review), verify |

The **orchestrator** is not a prompt in v0.1: it is the human plus the five commands.
`ship` is the only place `git commit` runs, from the main session, after an explicit yes.

**Designer** is an architect activity, not a builder flavour: the existing read-only UI
designer prompt writes into `design.md`, so in v0.1 it is a `ui` profile loaded during
`propose`; the builder builds what `design.md` specifies; the verifier carries the UI
checklist (contrast measured, state never conveyed by colour alone).

**Independence** comes from context separation, not from vendor. Claude plans and Codex
builds is a cost and skill choice. What is required: the verifier never shares a context
with the builder, and preferably not the builder's model.

## How a role reaches each tool

Claude: `.claude/agents/<role>.md` with frontmatter `name`, `description`, `tools`,
`model`, `effort`, `maxTurns`; the `verify` skill invokes it with `context: fork`. The
architect runs in the main session, not forked, because planning needs back-and-forth.
`git commit` for the builder is blocked by the PreToolUse guard, not by `disallowedTools`
(which would remove all of Bash). https://code.claude.com/docs/en/sub-agents

Codex, when invoked from Claude: no TOML needed. The role body goes in
`codex exec -c developer_instructions="..."` or prepended to the stdin prompt; standing
rules come from the root `AGENTS.md` (read root-down, 32 KiB cap, no import syntax).
`.codex/agents/<role>.toml` only if Codex becomes the cockpit.
https://learn.chatgpt.com/docs/agent-configuration/agents-md ·
https://learn.chatgpt.com/docs/config-file/config-reference

## Role prompt skeleton

Derived from the existing prompts, which share one shape:

```
# <role>                              who you are, the one constraint that defines you and why
## What you read from the project     layout, check command, settled and open decisions,
   every time                         from AGENTS.md, never from memory; if silent, say so and ask
## What you produce                   outputs and their exact shape
## Procedure                          cheapest evidence first, stop at first failure
## Working inside a change            openspec/changes/<x>/ is the brief, re-read from disk;
                                      proposal.md is the scope, tasks.md is not
## What to raise instead of deciding  open decision → name it and stop; design contradicts
                                      reality → stop and report, do not route around
## What you must not do               tick tasks.md, commit, fix what you found, widen scope
## How to report                      verdict first, worst first, certain vs suspected
                                      separated, show what actually ran, no manufactured findings
```

## Roles to add later, with triggers

- `reviewer` split from `verifier` when one verify pass no longer fits a context, or when
  cheap static review and browser verification want different models.
- `designer` as its own role when a project needs a mandatory spec-before-build UI gate.
- `orchestrator` prompt only if an unattended mode is ever built.
- `security-reviewer` when a project has an external attack surface.
- No `explorer`: both tools ship one.

## Decisions taken

1. Three roles in v0.1: `architect`, `builder`, `verifier`. Orchestrator is the human.
2. `builder` has a Claude subagent player, so the decision model may route a task to Claude.
3. Commits happen only in `ship`, from the main session, after an explicit yes. One
   commit per change in v0.1.
4. The verifier is a fresh-context Claude subagent. `codex review` is an optional feature,
   not a dependency of `verify`.
5. The "no ticking, no committing" rules live in the `sdd` rule set; each role body keeps a
   one-line reminder because a forked subagent may not load the rules file.
6. UI design is a `ui` profile of the architect in v0.1, seeded from the existing designer prompt.
7. `effort` has a fixed default per role; the decision model may override it per task.
8. Playwright MCP is declared on the Claude side only in v0.1.
